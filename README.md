# SQLite3 on ESP32 raw SD Card

This is a PoC for making SQLite3 to run on ESP32 with a raw SD card, all reads and writes are at block level, no filesystem needed, maximise the performance, save I/O and CPU.

## Caution

This is not production ready!

## Issues need to fix 

This is a to-do list generated by LLM auditing earlier. For my own reference only.

1. Broken Unaligned/Partial Reads & Writes:
    * Problem: The fsRead and fsWrite functions assume that all I/O requests from SQLite will be perfectly aligned to the SD card's sector size and be a multiple of the sector size. They calculate the number
      of sectors with simple division (nSectors = iAmt / sector_size), which truncates the value.
    * Impact: If SQLite requests a read or write of a size that is not a multiple of the sector size (typically 512 bytes), the operation will be incomplete, leading to silent data corruption. This is the most
      severe bug in the driver.
    * Fix: You must implement a read-modify-write mechanism. For a write that isn't sector-aligned or sized, you need to:
        1. Read the affected sector(s) into a buffer.
        2. Modify the buffer in memory with the new data.
        3. Write the entire sector(s) back to the card.

2. Incorrect Journal Detection and Deletion:
    * Problem: The code in fsOpen (for detecting an existing journal) and fsDelete (for deleting the journal) calculates the sector location of the journal header using BLOCKSIZE (the SQLite page size) instead
      of the card's sector_size.
    * Impact: Unless BLOCKSIZE happens to be exactly equal to sector_size, the driver will look in the wrong place for the journal. This will cause it to fail to detect existing journals on startup (risking
      database corruption during recovery) and fail to delete them properly.
    * Fix: Replace BLOCKSIZE with shared_file.pCard->csd.sector_size in the sector calculations within fsOpen and fsDelete. For example, the last sector index is (shared_file.nBlob / sector_size) - 1.

3. Potential for Stack Overflow Crash:
    * Problem: In fsOpen, the buffer for reading the journal header (last_block) is allocated on the stack with size BLOCKSIZE. BLOCKSIZE is defined as SQLITE_DEFAULT_PAGE_SIZE, which is often 4096 bytes and
      can be as large as 65536. This is a very large stack allocation for an embedded system.
    * Impact: This will likely cause a stack overflow and crash the device.
    * Fix: The buffer only needs to be large enough for the sectors being read. Since you are reading one sector to check for a journal, the buffer should be sector_size bytes.

4. Integer Overflow on Cards > 4GB:
    * Problem: The shared_file members nBlob, nDatabase, and nJournal are 32-bit integers (uint32_t or int). The card size calculation correctly uses int64_t but the result is stored in a uint32_t, which will
      overflow for cards larger than 4GB.
    * Impact: On a >4GB card, the VFS will have a completely incorrect understanding of the card's size, leading to unpredictable behavior and corruption.
    * Fix: Change nBlob, nDatabase, and nJournal in the shared_file struct to be int64_t.

5. Incorrect Handling of Reads Past EOF:
    * Problem: The xRead implementation does not correctly handle the case where a read request starts within the file but extends past the end of it. SQLite's VFS contract requires the driver to read the
      available bytes and zero-fill the rest of the request buffer. This implementation returns a SHORT_READ error without providing any of the valid data.
    * Impact: This may cause read failures or incorrect data being returned to the application.
    * Fix: Adjust the logic in fsRead to calculate the number of bytes that can be read, read them, and then memset the remainder of the user's buffer to zero.
